| 2026-09-23 | BE-0 | `CLOCK_OVERRIDE` sets "now" and the clock keeps ticking from it (offset, not frozen). It is ignored in prod. | 2026-09-23 | BE-0 | `VALIDATION_FAILED` uses HTTP 400 (415 for a wrong content type). Full per-code status table is in `api-contract.md` §5.1. | The plan lists codes but not statuses. Clients switch on `error.code`. |
| 2026-09-23 | BE-0 | `POST /v1/account` without `consent: true` returns `400 VALIDATION_FAILED` with `details.field = "consent"`. The account email and name come only from the verified token. | The plan says "requires consent" but gives no error. |
| 2026-09-23 | BE-0 | `GET /v1/taxonomy` returns `taxonomy.json` as-is, including the top-level `timezone`. | Android bundles an identical copy, so one shape is simpler. The extra field is additive. |
| 2026-09-23 | BE-0 | Unknown paths return `404 NOT_FOUND` in the §8.1 error body. A wrong method on a known path also returns `404` (not `405`). | A catch-all route is simpler and avoids StatusPages rewriting deliberate 404 bodies. |
| 2026-09-23 | BE-0 | Auth is a route-scoped plugin: `authenticated(verifier, users) { … }` (requires an account) and `authenticated(…, requireAccount = false)` (only `POST /v1/account`). Handlers read `call.principal` / `call.account`. | One way to guard routes. Forgetting it fails loudly (`error(...)`) instead of leaking data. |
| 2026-09-23 | BE-0 | `X-Request-Id`: a valid client-sent id (1–64 of `[A-Za-z0-9_-]`) is echoed, anything else is replaced, and requests are never rejected over it. Call logs contain only method, path (no query), status, duration, and request id. | Traceability without logging user data. |
| 2026-09-23 | BE-0 | `V2__seed_taxonomy.sql` is generated from `taxonomy.json` (v1) by `TaxonomySeedTest`, which fails if they drift. Later taxonomy changes need a new migration. | Single source of truth (plan §3) with append-only migrations. |
| 2026-09-23 | BE-0 | Tests use embedded PostgreSQL 17 (`io.zonky.test:embedded-postgres`, test-only) for migration and repository tests. | Real SQL coverage in CI without Docker or secrets. PG 17 matches Neon's default. |
| 2026-09-23 | BE-0 | Stubs: `StubReportService` and `StubInterventionEngine` are no-ops (return null/0/empty). `StubEntryRepository`, `StubPhotoAnalyzer`, and `StubGeminiClient` throw (501 / `GeminiException`). | Lets BE-1 call `onLateEntry` and BE-3 build reports before BE-3/BE-4 land. |
| 2026-09-23 | BE-0 | Docker image defaults to `APP_ENV=prod`. Staging must set `APP_ENV=staging` explicitly. | Safe default: no `.env`, no dev tools, no clock override. |
| 2026-09-23 | BE-1 | A PUT (or sync upsert) whose fields all equal the stored entry returns `200` in any week, including closed ones. | A retried create whose response was lost would otherwise get `WEEK_CLOSED` after rollover and make the app revert an entry that was saved (NFR8). |
| 2026-09-23 | BE-1 | Changing `createdAt` on update returns `400 VALIDATION_FAILED` (`field=createdAt`). The server truncates `createdAt` to milliseconds before storing and comparing. | The plan says updates "may not change createdAt" but gives no error. Millisecond truncation keeps round-trips exact (the API returns milliseconds, Postgres stores microseconds). |
| 2026-09-23 | BE-1 | Upsert of another user's id returns `409 CONFLICT` (plan §9 BE-1), but DELETE of another user's id returns `204` and deletes nothing. | DELETE of a missing id is `204`; treating a foreign id the same way doesn't leak that it exists. |
| 2026-09-23 | BE-1 | `GET /v1/entries` returns `{weekStart, weekEnd, editable, entries}` (not a bare array), and each entry carries `editable` and `updatedAt`. A non-Sunday `weekStart` returns `400`. | The plan doesn't define the shape. The wrapper is extensible, and `editable` saves Android from re-deriving week rules. |
| 2026-09-23 | BE-1 | Sync results are `{id, op, status, entry, message}`, with statuses `OK`, `WEEK_CLOSED`, `INVALID`, `INVALID_TIMESTAMP`, `CONFLICT`, `ERROR`. `WEEK_CLOSED` carries the server copy. At most 500 items per sync. Upserts run before deletes. Malformed items are decoded one by one, so they fail alone. | The plan lists only some statuses. The server copy lets the app revert (plan §10 AN-1). The cap bounds request time. |
| 2026-09-23 | BE-1 | Late creates call `ReportService.onLateEntry` after the entry is committed, once per affected week per request. If it throws, the error is logged and the entry save still succeeds. | The entry must never be lost over a report refresh. BE-3 may want a staleness check as a safety net (see HANDOFF). |
| 2026-09-23 | BE-1 | `DELETE /v1/account` needs a valid token but not an account. It deletes the `users` row (cascade) first, then the Firebase user (`USER_NOT_FOUND` counts as success). A Firebase failure returns `500` and a retry completes it. | Makes deletion idempotent and retryable after a partial failure (SFR4.2, NFR4). |
| 2026-09-23 | BE-1 | `GET /v1/export` runs `ReportService.catchUp` first (errors are logged, not fatal) and returns a versioned document (`format`, `exportVersion`) with reports nesting hotspots, recommendations, adoptions, and impacts. | The export should include every report the user is due. Nesting mirrors the report payload and is easier to read. |
